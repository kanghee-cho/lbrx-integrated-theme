# LBRX 통합 테마 설계

**상태: 구현 전 설계안.** 목적은 일곱 앱을 똑같이 보이게 하는 것이 아니라, 한 곳에서 바꾼 디자인 의도가 각 앱에서 같은 의미로 보이게 하는 것이다.

| 확인한 요구사항 | 설계 결정 |
|---|---|
| 장시간 글쓰기·읽기, 2026년 감성의 녹색 계열 | 저채도 배경과 청록 강조색을 쓰는 라이트·다크 한 쌍. 실제 색감은 시안이다. |
| 글꼴·크기·줄 간격도 관리 | 본문과 고정폭 글꼴을 분리한다. 앱이 지원하지 않는 값은 억지로 변환하지 않는다. |
| 색을 보면서 수정하는 Rust TUI | 색상 견본과 실제 문장·코드 미리보기를 함께 제공한다. 원본 파일도 직접 편집할 수 있다. |
| 한 명령으로 생성, 수동 가져오기 | 생성기는 앱 설정에 쓰지 않는다. 사용자는 원하는 앱의 산출물만 가져간다. |

1. [원본과 생성 구조](01-architecture.md) — 무엇을 어디서 바꾸며, 변경이 어떻게 일곱 앱에 전파되는가.
2. [팔레트와 편집 경험](02-design-and-editor.md) — 색상·서체 시안, TUI 조작, 읽기 편한지 판단하는 기준.
3. [앱별 적용 계약](03-targets.md) — 가져올 파일과 설정 위치, 상속·제한 사항, 구현 완료 조건.
4. [옵션 표시와 확장 전략](04-option-strategy.md) — 공통값과 앱별 예외가 보이는 화면, 같은 샘플의 앱별 차이, 새 옵션의 도입·승격 기준.
5. [사용 언어와 라이브러리 버전 관리](05-languages-and-dependencies.md) — 구현 언어·출력 형식, Rust 의존성 도입 기준, 버전 고정·갱신 절차와 대상 앱 검증 버전.

**사용 흐름 예시:** TUI에서 다크 모드의 청록 견본을 바꾸고 저장한다. `lbrx-theme build`를 한 번 실행해 양쪽 모드의 패키지를 다시 만든다. VS Code에는 새 패키지를 설치하고, Windows Terminal에서는 같은 이름의 배색표를 교체한다. 가져오기 전까지 기존 앱 화면은 변하지 않는다. 문서의 명령과 경로는 구현 목표이며 아직 제공되는 기능이 아니다.

## 다음 단계: 원본 모델과 `check` CLI

첫 구현은 TUI나 일곱 앱 전체 생성이 아니라 **테마 원본을 읽고 오류를 설명하는 최소 CLI**로 한정한다.

1. **개발 환경:** `rustup`, `rustc`, `cargo`의 실행 가능 여부를 확인한다. Windows MSVC 도구체인은 Visual Studio Build Tools의 C++ 빌드 도구와 Windows SDK도 확인한다. [버전 관리 기준](05-languages-and-dependencies.md)에 따라 Rust 버전을 검증·고정한다.
2. **패키지 구성:** 단일 Cargo 패키지에 `model`과 `resolve`, `check` 명령을 만든다. 이 단계에는 `serde`, `toml`, `clap`만 도입하고 `Cargo.lock`을 커밋한다. `edit`와 `build`를 아직 동작하는 명령으로 안내하지 않는다.
3. **원본 작성:** `themes\lbrx.toml`에 라이트·다크 팔레트, 필수 역할·ANSI 16색, 공통 서체를 정의한다. 설계 문서의 부분 예시를 완전한 유효 원본으로 오인하지 않도록 한다.
4. **완료 기준:** 유효 원본은 성공 종료하고, 스키마 불일치·필수 역할/ANSI 슬롯 누락·잘못된 색상/참조/크기·대비 미달은 모드·키·원인과 실패 종료 코드를 반환한다. `check` 전후 원본은 동일해야 한다.
5. **검증과 후속 작업:** 정상 입력, 대표 오류, 대비 임계값 경계를 테스트하고 버전 관리 문서의 Cargo 검사 명령을 통과시킨다. 그다음 Typora·Windows Terminal 어댑터와 `build`를 연결하며, TUI는 같은 모델·검사를 재사용한다.
