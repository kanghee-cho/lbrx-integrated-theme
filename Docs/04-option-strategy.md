# 옵션이 보이는 방식과 새 앱을 추가하는 규칙

설계 원칙은 **사용자가 정하는 값**, **앱에서 그 값이 표현되는 방식**, **그 결과를 확인하는 방법**을 분리하는 것이다. ‘공통’은 일곱 앱 모두가 지원한다는 뜻이 아니다. 예를 들어 ‘본문 최대 폭’은 문서를 조판하는 앱 사이에서만 공통이다. 이를 Vim의 자동 줄바꿈 열 수로 바꾸면 화면 모양이 아니라 편집 동작을 바꾸므로 매핑하지 않는다.

## 원본과 미리보기의 역할

공통값과 향후 지원할 앱별 예외는 원본 TOML에서 관리한다. TUI에서는 선택한 앱·모드의 견본만 보여 주며 값을 편집하거나 설치된 앱의 설정을 읽지 않는다. 앱별 예외가 추가되면 지원되는 범위에서만 공통값보다 우선한다. **앱에 맡김**은 해당 규칙을 출력하지 않는다는 뜻이다.

## 비교 화면: 같은 입력을 어디까지 재현하는가

같은 제목, 한글 문단 두 개, 링크, 인용, 코드 블록을 가진 **기준 Markdown 문서 한 장**을 사용한다. 색상 비교는 같은 문자열과 배경에서 하고, 조판 비교는 같은 창 너비·배율·설치 글꼴에서 한다. 다음 표는 실측 화면이 아니라 설계 시 기대하는 모습이다.

| 선택한 값 | 기준 모습 | 앱에서 달라지는 모습 |
|---|---|---|
| 라이트 `link → pine` | 본문 속 링크 글자는 청록 `#246958`, 밑줄로도 구분 | Typora 문서와 Obsidian 읽기 뷰는 링크를 강조한다. 라이브 프리뷰에서 편집 중 드러나는 Markdown 기호까지 링크처럼 칠하지 않는다. 터미널 ANSI 녹색은 별도 역할이므로 링크 변경에 따라 바뀌지 않는다. |
| 문단 간격 `0.8em` | 첫 문단과 다음 문단 사이에 여백. 한 문단 안의 줄 간격은 유지 | Typora와 Obsidian 읽기 뷰는 문단 블록에 적용한다. 라이브 프리뷰에서 빈 줄·커서 위치까지 바뀌는 경우는 동일 적용으로 표시하지 않는다. 안전한 매핑이 확인되기 전에는 해당 뷰만 앱에 맡긴다. |
| 고정폭 크기 `16px` | 코드 샘플의 기준 글자 크기 | VS Code는 별도 설정 조각에 `16px`에 해당하는 수치를, Windows Terminal은 프로필 조각에 `12pt`를 제안한다. Helix·터미널 Vim은 호스트 서체를 사용한다. 어느 쪽도 배색 파일만 가져와서는 글자 크기가 바뀌지 않는다. |

TUI 견본은 다른 앱에 같은 역할이 어떻게 쓰이는지 색으로 확인하는 도구다. 실제 문서 폭·간격·폰트·뷰를 확인하려면 대상 앱에서 같은 샘플을 열고 앱 버전·뷰·호스트를 기록한다.

## 옵션 계약: 값의 출처와 지원 방식을 분리한다

원본에는 사용자 선택만 저장한다. 옵션의 의미와 매핑은 저장소 안의 Rust 정의로 관리한다. 별도 플러그인 시스템이나 앱별 설정 파일 복사본은 두지 않는다.

| 정의 | 기록할 내용 |
|---|---|
| 옵션 명세 | 안정적인 키(예: `document.max_width`), 한국어 표시명, 범위(공통·문서·앱 전용), 타입·단위·허용 범위, 모드 공유 여부, 값이 없을 때 동작 |
| 앱별 매핑 | 옵션 키 + 대상 앱·뷰, 지원 방식(**직접 / 변환 / 호스트 상속 / 미지원**), 전달 경로(**테마 / 별도 설정 조각 / 수동 안내 / 출력 없음**), 변환·제약과 확인용 샘플 |
| 값의 출처 | 공통값, 앱별 예외값, 명시적 ‘앱에 맡김’. 예외가 없으면 공통값을 따르고, ‘앱에 맡김’은 공통값이 있어도 해당 규칙을 생략한다. |

TUI와 생성기는 같은 해석 결과를 사용한다. 예를 들어 Windows Terminal의 크기는 `공통값 · 변환 · 별도 설정 조각`이다. **변환된 값이 있다는 것과 배색을 가져오면 적용된다는 것은 다르다.** 호스트 상속이나 미지원은 편집값으로 저장하지 않는다. 미지원 대상에 예외를 직접 입력한 원본은 `check`에서 키와 이유를 알린다.

## 확장 규칙: 새 앱이 생겨도 공통 메뉴는 자동으로 늘지 않는다

1. **기존 역할부터 연결한다.** 새 어댑터는 기존 옵션별로 앱·뷰의 지원 방식과 전달 경로를 선언한다. 기존 키의 의미와 단위가 맞으면 재사용하고, 이름만 비슷하거나 편집 동작을 바꾸면 연결하지 않는다.
2. **새 개념은 가장 좁은 범위에서 시작한다.** 예를 들어 Obsidian 콜아웃의 모서리 반경은 `apps.obsidian.callout_radius`라는 선택 항목으로 시작한다. 기본은 미설정이며 기존 테마 출력에는 새 규칙이 생기지 않는다. 폴딩·줄 번호 표시 같은 앱 동작은 테마 옵션에 넣지 않는다.
3. **두 번째 앱이 필요로 할 때 승격을 검토한다.** 사용자 의도, 적용 대상, 단위, 기준 샘플의 기대 결과가 같을 때만 `document.callout_radius`로 올린다. 새 앱이 비슷한 박스를 그린다는 이유만으로 일반 인용문까지 둥글게 만들지 않는다.
4. **승격해도 기존 모습은 유지한다.** 기존 전용 키는 전환 기간에 *그 앱의 예외값*으로 해석하고 대체 키를 안내한다. 기존 값이 다른 앱으로 퍼지지 않는다. 같은 예외를 구·신 표기로 중복 선언하면 오류다. 선택 키 추가는 기존 원본을 고치지 않아도 되며, 기존 키 제거·단위 의미 변경은 스키마 버전 변경과 명시적 마이그레이션 대상이다.

**새 어댑터 승인 기준:** 기존 원본을 그대로 빌드했을 때 기존 대상의 테마 내용이 같아야 한다. 새 대상에서는 대표 공통값 하나의 전파, 앱별 예외의 격리, ‘앱에 맡김’의 규칙 생략을 확인한다. 마지막으로 지원한다고 선언한 각 뷰에서 기준 샘플을 열어 비교한다. 재현하지 못한 차이는 공통값을 바꾸어 숨기지 않고 해당 매핑의 제한으로 남긴다.
