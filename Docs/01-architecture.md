# 원본과 생성 구조

```text
themes\lbrx.toml                 팔레트·역할·서체·ANSI 공통 원본
themes\languages\*.toml          공통 토큰 매핑 + 언어별 예외
themes\editors\*.toml            앱별 색상 옵션
    ↓ 저장된 파일 읽기
Rust CLI ─ check / build
    ↓ 두 모드의 참조 해석 → 타입·대비 검사 → 앱별 변환
dist\lbrx\<target>\              가져올 파일, 옵션 설정 예시, 설치 안내
```

**팔레트는 실제 색, 역할은 색의 용도, 어댑터는 앱에서의 표현을 정의한다.** 강조색 전체를 바꾸려면 `pine`을 수정하고, 링크만 파랗게 하려면 `link` 역할을 `slate`에 연결한다. 구문색은 개별 언어 → `languages/common.toml` → 기본 역할 순으로 찾는다. 앱 전용 키는 `editors`에만 두고, 공통 원본에는 CSS 선택자나 Vim 그룹을 넣지 않는다. 자세한 사용법은 [설정 파일과 우선순위](02-design-and-editor.md#언어별-구문색과-앱-전용-옵션)를 참고한다.

```toml
# 원본의 일부. dark에도 같은 키 집합이 필요하다.
schema_version = 1
[light.palette]
paper = "#F3F4EC"
ink = "#24362F"
pine = "#246958"
slate = "#43617B"

[light.roles]
background = "paper"
text = "ink"
accent = "pine"
link = "pine"
```

| 토큰 집합 | 계약 |
|---|---|
| 모드별 팔레트 | 불투명 sRGB `#RRGGBB`. 역할은 같은 모드의 팔레트 키만 참조한다. |
| 모드별 역할 | UI(본문·표면·선택·포커스), 문서(제목·링크·인용·인라인 코드), 구문(주석·문자열·키워드·함수·숫자), 상태(오류·경고·성공), 터미널(전경·배경·커서). 같은 색을 써도 의미가 다르면 키를 분리한다. |
| 문서 코드 블록 배경 | 선택 역할 `code_block_background`는 Typora·Obsidian의 여러 줄 코드 블록에만 사용한다. 생략하면 문서 기본 배경을 사용한다. |
| ANSI 슬롯 | `[light.ansi]`와 `[dark.ansi]`에 키 `0`부터 `15`까지 모두 두고, 각 값은 같은 모드의 팔레트 키를 참조한다. |
| 공통 서체 | `[typography.prose]`와 `[typography.mono]`에 우선순위 있는 글꼴 목록 `families`, 기준 크기 `size_px`(CSS px), 줄 높이 `line_height`(배수)를 둔다. 목록은 비어 있지 않아야 하며 수치는 유한한 양수여야 한다. 앱 단위 변환은 어댑터 책임이다. |

**Rust 구성:** `model`은 기본 TOML 구조를 정의하고, `layers`는 원본과 같은 디렉터리에 있는 언어·앱 설정을 함께 읽는다. `resolve`는 양쪽 모드의 참조와 대비를 검증한다. `check`는 원본을 검사만 하고 `build`는 앱별 결과 파일과 설치 안내(`README.md`)를 생성한다.

**실패와 재생성:** `check`는 원본을 변경하지 않는다. 스키마 버전 불일치, 누락된 역할·ANSI 슬롯, 알 수 없는 참조, 잘못된 크기나 필수 대비 미달은 모드·키·원인을 표시한다. `build`는 선택한 대상을 임시 출력에 생성·검사한 뒤에만 기존 생성본을 교체한다. 실패 시 직전 생성본을 보존한다. 같은 원본과 도구 버전에서는 선택한 대상의 출력이 바이트 단위로 같다. `dist` 수동 편집은 해당 앱의 재생성에서 사라지므로 변경은 원본에 한다.

## 출력과 복구

`build`는 역할과 ANSI를 HEX로 해석하고 언어·앱 매핑과 함께 `dist\lbrx\resolved.toml`에 기록한다. 역할 키는 정렬하고 ANSI는 슬롯 0–15 순서로 저장한다. 생성 시각·임시 경로를 출력에 넣지 않으며 같은 원본·도구 버전의 출력은 바이트 단위로 같다. 앱별 파일과 설치 방법은 [앱별 적용 계약](03-targets.md)을 참고한다. 원본과 앱 설정은 변경하지 않는다.

**게시 절차**

`build`에서 `--app`을 생략하면 모두 생성한다. 선택 빌드에서는 기존 미선택 앱 파일의 내용을 그대로 보존하며, 없던 앱 폴더는 생성하지 않는다. `resolved.toml`은 항상 이번 빌드의 원본을 반영하므로, 선택 빌드 직후 미선택 앱의 파일은 이전 원본을 반영할 수 있다. 모든 앱의 출력을 동기화하려면 전체 빌드를 실행한다.

1. 원본 검증·해석·직렬화를 먼저 수행한다. 잘못된 원본은 출력 폴더를 만들거나 변경하지 않는다.
2. `dist\.lbrx-build.lock`을 배타적으로 생성해 동시 빌드를 거부한다. `dist\.lbrx-build`에 임시 파일을 쓰고 원래 생성 내용과 바이트 단위로 일치하는지 확인한다. TOML과 JSON은 다시 파싱하고, VSIX는 ZIP을 열어 매니페스트 엔트리와 테마 등록 및 JSON 구조를 확인한다.
3. 기존 `dist\lbrx`가 있으면 생성물 형식의 `resolved.toml`과 허용된 앱 산출물만 있는 실제 디렉터리인지 검사한다. 선택 빌드에서는 이 검사를 거친 기존 미선택 앱 파일을 임시 출력에 복사한다. 알 수 없는 파일·하위 폴더·링크는 삭제하지 않고 교체를 거부한다.
4. 기존 출력을 `dist\.lbrx-previous`로 옮긴 뒤 임시 출력을 `dist\lbrx`로 옮긴다. 두 번째 이동 실패 시 기존 출력을 원래 위치로 복구한다. 복구도 실패하면 보존된 백업 경로를 오류로 알린다.
5. 성공 후 이전 백업을 정리한다. 임시 출력·잠금 정리 실패도 오류로 알리며, 새 출력 게시 후 백업 정리만 실패한 경우에는 그 상태를 명시한다.

이 방식은 일반적인 오류에 대한 롤백이며 **프로세스 강제 종료·정전까지 보장하는 단일 원자적 디렉터리 교체는 아니다.** 두 번의 이동 사이에는 출력 경로가 잠시 없을 수 있다. 작업 중단 흔적이 있으면 자동 삭제·재시도하지 않는다. 실행 중인 빌드가 없는지 확인한 뒤, `.lbrx-previous`가 있고 `lbrx`가 없으면 백업을 `lbrx`로 복원한다. 두 폴더가 모두 있으면 내용을 확인해 어느 쪽을 보존할지 판단한다. 필요한 내용을 보관한 후 남은 임시 디렉터리·백업·잠금을 수동 정리하고 다시 실행한다.

## 옵션 확장 기준

1. 같은 의미와 단위의 공통 역할을 우선 재사용한다. 앱에서 직접 적용하는지, 환산한 설정 조각을 제공하는지, 호스트 설정에 맡기는지 구분한다.
2. 새 옵션은 가장 좁은 앱·뷰 범위에서 시작한다. 타입·단위·허용 범위·생략 시 동작을 기록하고, 명시하지 않은 선택 옵션으로 기존 출력을 바꾸지 않는다.
3. 여러 앱에서 사용자 의도·단위·적용 범위가 같을 때만 공통 옵션으로 승격한다. 기존 키의 의미·단위를 바꾸거나 삭제하려면 명시적인 스키마 마이그레이션을 검토한다.
4. 설정 전파·앱별 예외의 격리·생략 동작을 생성 테스트로 확인한다. 실제 화면은 같은 샘플과 글꼴·창 너비에서 비교하고 앱 버전·OS·뷰·모드를 기록한다.

[Helix 옵션 대장](17-helix-options.md)과 [VS Code 옵션 대장](19-vscode-options.md)은 생성기가 지원 스코프·색 ID를 판정할 때 읽는다. 해당 대장의 표 구조와 VS Code 색인 제목을 바꿀 때는 어댑터의 파서와 테스트도 함께 확인한다.
